## Architecture and correctness rules

Keep rules/engine/games/ratings/analysis/academy/federation/exchange/ledger/storage modules separate from UI. Domain commands validate and commit atomically; React reads state rather than mutating money/history. Use typed score perspective, actual achieved depth, legal PV validation, per-ply pre/post hashes, full history-sensitive cache keys and request-generation cancellation. Never run deep engine analysis on the interface thread.

Game/result/rating/report-intent finalization and market settlement need unique idempotency keys. Multi-tab single-writer fencing, crash/retry recovery, deterministic event/RNG state and versioned schema migrations are essential. Keep completed games and historical reports unless the player explicitly deletes them. Low quota pauses work and offers export; it never truncates old games. Browser local storage is not a guarantee against OS eviction: implement external backup/export and clear truthful status.

Use Glicko-2 reference equations and tests, documented rating periods/eligibility/initialization and distinct time-control pools. Ratings are internal Crown ratings, never FIDE equivalence. Ratings, trading skill and chess-specific development are separate. No general IQ claims. Skill observations need opportunity counts/source links/confidence; empty data stays insufficient. Training memorization is excluded from held-out measurement.

LMSR formulas, bound caveats for nonuniform initialization, fees, rounding, balance-sheet conservation and settlement contracts are in document09. Full offline ownership means determined save tampering cannot be prevented absolutely; implement honest-play integrity, not a false cryptographic security claim. Keep all money fictional. Market probabilities are not guaranteed outcomes.
